# [OM] Fix integer shift folders for out-of-range shift amounts

Fixes: <!-- fill in the issue number(s) -->

## Problem

Folding `om.integer.shl` or `om.integer.shr` with a large constant shift amount trips APInt assertions (`ShiftAmt <= BitWidth`). `om-elaborate-object` and `--canonicalize` both reach the folders.

## Reproducer

```mlir
om.class @ShlTruncExtend58() -> (result: !om.integer) {
  %c1 = om.constant #om.integer<1 : si64> : !om.integer
  %c2 = om.constant #om.integer<4294967290 : si64> : !om.integer
  %result = om.integer.shl %c1, %c2 : !om.integer
  om.class.fields %result : !om.integer
}
```

```sh
circt-opt '-om-elaborate-object=all-public-classes=true allow-unevaluated=true' repro.mlir
```

- Before (main @ 4738bd2685, assertions on, `--verify-each`): exit 134, `circt-opt: sdk/include/llvm/ADT/APInt.h:788: APInt &llvm::APInt::operator<<=(unsigned int): Assertion `ShiftAmt <= BitWidth && "Invalid shift amount"' failed.`
- After: exit 0, `repro.mlir:4:13: error: 'om.integer.shl' op shift result must not exceed 16777215 bits`

## Root cause

`IntegerShrOp::fold` hands the 64-bit shift amount to `APSInt::operator>>`, which takes an `unsigned` no larger than the bit width: amounts at or above the width assert, and amounts of 2^32 or more are silently truncated (so `x >> 2^32` would fold to `x`). `IntegerShlOp::fold` extends the operand to `width + shiftAmt` bits, but that sum is truncated to `unsigned` before the shift, so the shift amount exceeds the new width. The folded value is an `IntegerAttr`, whose width is capped at `IntegerType::kMaxWidth` (2^24 - 1).

## Fix

`shr`: clamp the amount to the bit width (an arithmetic shift by the width or more leaves only sign bits). `shl`: if the result would be wider than `IntegerType::kMaxWidth`, emit an op error and do not fold, matching the folder's existing checks for negative and non-64-bit amounts.
