## Contract 2.3 (W-23, 2026-09-15)

- **What changed.** One field added to `FeedbackEntry`: `error_line`, the probe's own first `error:` diagnostic, bounded at 200 characters. One key added to `LedgerEntry.observed`: `cached_tokens`, a SUBSET of `tokens_in` and never a summand of it. One field added to `RunManifest`: `shard`, the `K/N` of `--shard` or null.
- **Why (`cached_tokens`).** The SDK reports `usage_metadata.cached_content_token_count` and nothing captured it, so the run could not say how much of its input was served from the context cache. `budget.yaml` registers exactly two rates, so the ledger still prices every input token at the list rate and the USD total is an UPPER BOUND; the count is what the size of the overstatement can be computed from. Google's cached-input rate for `gemini-3.8-flash` is USD 0.075 per million tokens through 2026-12-31 (VERIFIED 2026-09-15, `ai.google.dev/gemini-api/docs/pricing`); it is recorded in `llm.CACHED_INPUT_RATE_USD_PER_M` and read by nothing, because a third rate added after the registration commit would not be the file the campaign was registered against (FR-14.7). `cloud.google.com/vertex-ai/generative-ai/pricing` could not be read: its pricing table is not present in the fetched document.
- **Why (`shard`).** The seeded arm is embarrassingly parallel over seeds and a campaign that runs its corpus on more than one machine has to say which part of it each run drove, or its counts read as the whole corpus's. `--shard K/N` keeps the seeds at positions `index % N == K` of the already-fixed corpus order (`--seed-sha` still narrows first), and the manifest and section 0 of `results.md` both carry the string.
- **Why (`error_line`).** MEASURED, campaign 1 run `903a37c8`, seed 2: all five probes were `parse_error` at the build commit and `feedback.py` counted `parse_error` among `_ABANDON_STATUSES`, so the seed was abandoned WITHOUT the next turn ever being told what the tool said. A parse error is the loop's own mistake and it is repairable; it now feeds back with its diagnostic and the instruction to fix or replace the input, while `timeout` and `oom` stay abandoned.
- **Compatibility.** MINOR. `check_version` compares the MAJOR half only (`03-LLD.md` §2.2), so a 2.0, 2.1 or 2.2 instance still loads. `from_json` required EVERY declared field, which made that promise false the moment a MINOR added one to a member: pilot 8's stored `manifest.json` is a 2.2 payload with no `shard` and it failed E002. It now requires only the fields that carry no default - the structural ones - and an older payload loads with the default for what it has not got. `FeedbackEntry` is nested and was never affected.
- **The fixture set.** Every `contract_version` string under `contract/fixtures/` and `tests/fixtures/` moved to `2.3`; every `FeedbackEntry` in a `feedback_bundle` fixture gained `"error_line": null`, every `observed` block gained `"cached_tokens": null` and every `run_manifest` fixture gained `"shard": null`. No other byte of any fixture changed.

## Contract 2.4 (D-13, 2026-09-15)

- **What changed.** One value added to `BuildStatus` and one to `OracleClass`: `verifier_error`. Two fields added to `ProbeResult`: `verifier_message` and `verifier_op`, non-null exactly on that class. No dataclass, no `generate` signature, no serialiser; one validator rule, about the new pair.
- **Why.** MEASURED, campaign 2: ten of ten probes of one seed run `circt-opt --convert-moore-to-core` and exit 1 with `error: 'comb.extract' op result #0 must be a signless integer bitvector, but got '!hw.array<2xi2>'` and `error: 'llhd.sig.extract' op result #0 must be ref of a signless integer bitvector, but got '!llhd.ref<!hw.struct<a: i2, b: i2>>'`. Neither op is in the input: the conversion pass created them with aggregate types and MLIR's verifier refused the compiler's own output. `probe_task.classify_build` booked every exit-1-with-`error:` run as `parse_error:tool_rejected_input`, so the oracle never fired, the taxonomy charged the failure to the loop, and `feedback.py` told the model to fix an input that was fine.
- **What separates the two.** §4.8's parse-and-verify command for the input's own language, run on the input alone on the same `circt` worker inside `probe_execute`; exit 0 says the input is valid and the failure is the tool's. That test alone is NOT enough, which is measured too: recorded mutation probe `p-b3831e4112d4` is `circt-opt -lower-handshake-to-hw` on an input the loop fed without `--split-input-file`, and it exits 1 with `'builtin.module' op multiple candidate top-level modules detected ...` on an input that parses and verifies. A pass writes that sentence by hand; MLIR's GENERATED verifier writes `<operand|result|region|successor> #N must be ...` and `... failed to satisfy constraint: ...` and nothing else. Both conditions are required (`probe_task._GENERATED_VERIFIER`, `probe_task.verifier_upgrade`).
- **Downstream.** The fingerprint basis is `verifier`: the op, the message with every quoted op name and type generalised to `T`, and the pass the argv names, so two probes that break one invariant on one op with different aggregate types are one candidate. Reduction's interestingness test for the class checks exit 1, the op and the invariant, never the concrete type. Gate question 3 reads stage 3's parse-and-verify run rather than asking again, and question 4 is as for any other class. Repair does not take the class: `REPAIR_CLASSES` is unchanged. A `verifier_error` probe is a FINDING in the feedback bundle, never an input the next turn is told to fix.
- **Compatibility.** MINOR. `check_version` compares the MAJOR half only (`03-LLD.md` §2.2), so a 2.0 to 2.3 instance still loads, and the two new `ProbeResult` fields carry defaults, so a 2.3 payload loads with them null. `03-LLD.md` §6.2's `oracle_verdict` and `fingerprint` are compared byte for byte by `T-U-store-01` and could not move: the two `OracleVerdict` fields are the `verifier_error` table, appended to the schema as `registration` and `turn_failure` are, and `fingerprint`'s widened `CHECK` is `store._DDL_FINGERPRINT`, which creates the table before §6.2's own `CREATE TABLE IF NOT EXISTS` for it. `store.widen_fingerprint_basis` moves a store created before 2.4 and `--reclassify` calls it.
- **The fixture set.** Every `contract_version` string under `contract/fixtures/` and `tests/fixtures/` moved to `2.4`; every `ProbeResult` fixture gained `"verifier_message": null` and `"verifier_op": null`. No other byte of any fixture changed.
